# Reference dashboard redesign

## Live-3 update

The current presentation follows `sleep_dashboard_live-3.html`: energy and productive-hours summaries with previous-week changes; a three-band energy/productivity/sleep overview; sleep-versus-next-day-energy scatter; separate midday/evening energy columns; daily outcome cards; complete daily and weekly tables; and a coverage/timing-conflict analysis summary. The authenticated React/API bridge and minute-level heart-rate onset zoom are retained. The new file's embedded credentials, direct Supabase queries, sample generators and password login are not used. Productive hours come from the numeric evening-response field; zero is a recorded value, while missing answers remain null.

Jack's presentation is limited to study/wake dates 6–19 October 2026. Because weeks are grouped by the preceding night, only the weeks starting 5 and 12 October are navigable. The week starting 19 October and later records are hidden from the dashboard; database data and API access grants are unchanged. The frontend caps its requested range, daily navigation and initial URL date to this study window for P001_DEMO.

Daily and weekly at-a-glance narratives now appear above the charts. `glanceSummaries.ts` generates them from the selected study records and sends them through the existing frame data bridge. Daily text reports sleep, self-reported productive hours and steps, with a comparison to the immediately preceding calendar day only when paired values exist. Weekly text reports the observed averages and recorded step total. When there are at least four sleep/productivity pairs and at least two days in each group, it compares productive-hour means for nights below the paired-data median sleep duration versus nights at or above it. It does not impose a medical sleep target, force a productivity decline, treat missing values as zero or describe steps as a productivity measurement. Regression tests cover reversed associations, zero/missing values, insufficient variation and the existing week/date boundary.

The time-to-fall-asleep chart shows blue band dots (first recorded asleep stage minus recording start) and orange Your response dots (reported sleep onset minus reported bedtime). The horizontal axis shows nights. Questionnaire dots are slightly offset so equal values remain visible. Hover and accessible labels show each series' source timestamps. Missing answers are not generated and band timing is independent of questionnaire availability. The two series use different starting points; the former signed onset-versus-bedtime conflicts are not plotted here.

The dashboard uses the supplied `sleep_dashboard_gui.html` as the visual reference. Its cream/purple theme, panels, custom SVG charts, day/week navigation, tables and legend are retained in `frontend/src/dashboard/referenceDashboard.html`. This presentation is isolated in a sandboxed frame so its styles do not conflict with the rest of the React app. The prototype password gate, sample generators, direct database access and Supabase CDN client have been removed.

`ReferenceDashboardPage.tsx` remains behind the existing Google/Supabase session gate. React fetches only the participants granted by the Python API, retrieves records in bounded 31-day windows, and sends a display model to the frame. The frame never receives access tokens or database credentials. Messages requesting data or logout are accepted only from that frame's window. Legacy study routes retain the existing layout; participant/day/night/week routes use the reference design.

`referenceData.ts` pairs a night with its following wake date in Europe/Amsterdam civil time. It uses recorded sleep-stage boundaries for onset and wake time, the main session (or longest when no main is marked), sample-weighted hourly heart-rate aggregates, observed peak values, daily step totals and questionnaire answers. The existing demo variation remains applied by the backend. The range API now also returns sleep sessions and hourly observed peaks; the additions are backward compatible.

Important interpretation details:

- Band-stage onset is not described as a new heart-rate-derived sleep algorithm.
- Night heart rate covers 22:00–06:00 across midnight; day covers 06:00–22:00. Weekly aggregates use hourly bins; the daily sleep-onset chart loads one-minute observed averages through the authorized `/participants/{code}/sleep-comparison?date=...` endpoint. That endpoint is limited to two calendar days. Missing minutes remain gaps. Markers show reported bedtime, reported onset and Fitbit stage onset. The 20-minute before/after heart-rate averages are sample-weighted observations, not a sleep-onset detector.
- Active minutes are removed from all dashboard selectors, cards, charts, tables and legends. Exact peak timestamps and reported awakenings are unavailable and remain missing. Stage awakenings count recorded awake periods of at least ten minutes within the main sleep period.
- All questionnaire submissions stay in the API/model. Comparisons use the latest answer on a study date. Rating scales are 1–5.
- On 10 November, the owner confirmed that early-morning questionnaire times refer to the study date. Nine P001_DEMO morning records were aligned accordingly; their old dates were retained in provenance and the importer honors the correction on reruns. Noon/afternoon legacy answers were not reinterpreted. Negative or inconsistent intervals remain missing. When Fitbit onset precedes reported bedtime, the daily view explicitly flags the conflict. The measured table shows recording-start to first asleep stage, explicitly labelled as band lead-in rather than reported-bedtime latency. Recorded efficiency divides the original exported asleep minutes by the full band recording duration, using elapsed UTC time; it does not depend on questionnaire bedtime or adjusted demo sleep totals. Invalid or unavailable intervals remain missing. This percentage describes the recorded sleep period, not a clinical score or a measurement of when the participant got into bed. If no consistent pairs exist, the weekly card shows recorded sleep and awake minutes instead of an empty time-in-bed donut.
- Check-in completeness assumes one morning/midday and one evening response per recorded study day; there is no claim that a questionnaire link actually expired.
- Weekly averages exclude missing values; tables provide the current and preceding observed week. Partial boundary weeks use only dates present in the selected participant's record range.

Validation includes frontend alignment/missing-data/DST tests and backend authorization/range tests. The presentation was also exercised against the actual demo dataset through every week/day, with no rendering exceptions or invalid SVG coordinates. Desktop and mobile layouts were rendered in headless Edge. Verification snapshots are local under ignored `output/` and contain participant data; do not commit them.
